Cómo está construido

Un store,
dos transportes

La app es un prototipo estático con módulos ES. El estado vive en un único store observable, persistido en localStorage. Las pantallas nunca llaman a fetch: pasan por core/api.js, que puede responder local o contra un backend real sin cambiar una línea de UI.

Arranque

index.html
  └─ main.js
       ├─ loadStore()        // products.json + service.json + localStorage
       ├─ createApi(store)   // ?api=local | ?api=remote
       ├─ mountChrome()      // header, nav, sheets, toasts
       ├─ setupMotion()      // GSAP + ScrollTrigger
       └─ createRouter()     // renderiza la ruta del hash

Antes de cargar datos se muestran skeletons. Si el JSON no carga (por ejemplo, abriendo con file://), se explica cómo levantar el servidor en vez de dejar la pantalla en blanco.

Estado y persistencia

La clave es mega.v4. El store guarda una copia completa y la reescribe en cada commit().

{
  products: Product[14],
  categories: Category[8],
  service: { meta, items, faq },
  cart: [{ productId, colorId, qty }],
  favorites: [productId],
  orders: Order[18],
  profile: { name, phone, email, address, city, region },
  settings: { notifications, biometrics, newsletter },
  checkout: { payment, delivery },
  lastOrderId: "MT-1043" | null
}

Reglas de mutación

  1. Una acción por cambio. addToCart, setQty, toggleFavorite, createOrder, updateProduct…
  2. Validar antes de escribir. Stock, cantidades y campos obligatorios.
  3. Commit único. Persistir y notificar a los suscriptores una sola vez.
  4. Derivar, no duplicar. Totales, contadores y métricas se calculan con getters.

Los dos modos de API

Local · por defecto

?api=local o sin parámetro. Cada método espera 90–210 ms para simular red y resuelve contra el store. Funciona offline y no necesita servidor de API.

Remoto · ?api=remote

Hace fetch a /api/.... El mock de api/mock/server.mjs implementa el mismo contrato. La UI no cambia.

const api = createApi(store);
await api.createOrder(payload); // local o HTTP, misma firma
await api.updateProduct(id, { stock: 12 });

Router y ciclo de vida

  • Hash routing: #/ruta?query. No requiere rewrites en Vercel.
  • Cada navegación incrementa un token; una carga vieja no puede pisar la nueva.
  • Guarda scrollTop de #view por ruta y lo restaura al volver.
  • onBefore: cleanup() de GSAP, cierra sheets, begin(view) y actualiza el chrome.
  • onAfter: pageIn, reveal, tiltCards, ScrollTrigger.refresh().
  • Los módulos de pantalla se cargan con import(): el primer render solo baja Home.

Movimiento

GSAP + ScrollTrigger se cargan como globales vendorizados. motion.js expone begin, cleanup, pageIn, reveal, tiltCards y heroParallax. Si las librerías no están, cae a IntersectionObserver y, con prefers-reduced-motion, muestra todo sin animación.

Una animación nunca oculta contenido para siempre. El CSS base deja [data-reveal] visible si no hay JS; la clase .js activa el estado inicial y el observer lo revierte.

PWA

manifest.webmanifest define nombre, colores, iconos y modo standalone. El service worker (app/sw.js) se registra solo si la URL incluye ?sw=1, para no interferir mientras se edita. 

# activar caché offline
http://127.0.0.1:8787/app/?sw=1#/home

Rendimiento

  • Sin framework ni build: HTML + CSS + módulos nativos.
  • 14 productos y arte SVG inline: no hay imágenes de red.
  • Fuentes locales con font-display: swap.
  • Three.js solo en Home y solo si hay WebGL; se descarta al salir.
  • Listas cortas: re-render completo es más simple y más rápido que un diff manual.

Seguridad y límites

Qué protege el prototipo

  • No hay secretos en el frontend.
  • No se piden datos de tarjeta reales.
  • Los totales se recalculan al crear la orden en un backend real.
  • El CSV se genera localmente con datos del propio usuario.

Qué falta para producción

  • Autenticación y roles (admin/cliente).
  • Validación de stock y precios en servidor.
  • Pasarela de pago con webhooks firmados.
  • Base de datos, auditoría y backups.
  • Rate limiting y CORS restringido.
